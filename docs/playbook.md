# 微工具 playbook v1

> 版本：v1（2026-10-19）· owner：factory-lead · 来源：blurface 实验（BING-20 调研 + P0/P1 交付 + 验收卡）
> 变更规则：章节改动在 issue 里留一条 3-5 行 ADR-lite，再改本文件；不在聊天里口头改标准。

本手册是「微工具工厂」的标准作业程序：从机会调研到 kill/scale 的每一步，都以本文件为准。遇到手册没覆盖的情况，按第 1 章的总原则现场决策，事后补一条 ADR。

---

## 0. 怎么用

新项目从第 2 章开始，按顺序推进，不跳步：

```
机会调研（第 2 章） → gate 1 立项（第 3 章） → P0 IA 骨架（第 4/5 章）
   → P1 工具本体（第 4 章） → 验收（第 6 章） → 上线读数（第 8 章）
   → 变现（第 7 章，需 gate 4） → 加码 / kill（第 8 章，需 gate 5）
```

- **五道 gate 之外全部自主决策**，不要为了「确认一下」去请示：gate 1 立项、gate 2 花钱、gate 3 生产部署与域名、gate 4 变现开启、gate 5 kill/scale。
- 每个 gate 的请示与结果都回帖到项目 issue 留痕（一页纸/清单/读数截图），聊天结论不算留痕。
- 一次只推进一个站点的一个里程碑。并行的只有「调研下一个」这种零成本动作。

## 1. 总原则

### 1.1 工程总原则（成员钦定，最高优先级）

1. **可扩展优先，但拒绝过度设计。** 默认选能跑通的最简单结构；不为想象中的需求建抽象、建插件系统、建配置层。
2. **抽象进共享层必须有第二个真实使用者**，或成员已批准的明确计划。只有一个使用方的代码留在项目内。
3. **模块边界清晰。** 核心逻辑写成框架无关的纯 TS；UI 只做薄壳（接线、布局、交互）；配置外置到 `lib/*.ts`，不散落在 JSX 里。
4. **重大设计决策写 3-5 行 ADR-lite**，放进项目 issue（模板见 1.4）。
5. **先跑通再优化。** 禁止投机性重构；改共享库前先列出全部使用方影响。

判断句式：

- 「以后可能要支持 X」→ 不做。
- 「第二个站点也要这段代码」→ 才进 `packages/`。
- 「这个页面文案还没写」→ 先写文案，别先写组件抽象。
- 「这样更优雅」→ 除非同时更快/更少依赖，否则不做。

### 1.2 五道 gate（只在这些点请示）

| Gate | 触发时机 | 交付给成员的请示内容 | 谁能拍板 |
|---|---|---|---|
| 1 立项 | 调研完成 | 一页纸（第 3 章） | 成员 |
| 2 花钱 | 域名/付费服务/广告 | 用途、金额、替代方案、不花的后果 | 成员 |
| 3 生产部署与域名绑定 | preview 验证通过后 | preview 链接、验收结果、切流与回滚方案 | 成员 |
| 4 变现开启 | 读数达标后 | 付费点、定价、对现有免费层的影响 | 成员 |
| 5 kill/scale | 8 周读数 | 数据、建议、下一步资源投入 | 成员 |

红线（绝对不做）：不执行支付；不动生产域名/DNS（gate 3 批准前）；站点之间不互链成 network；不用 AI 填充正文；不抄竞对代码/素材/文案/商标；不删除不可再生资产；不破坏共享库既有接口。

### 1.3 完成定义（DoD）

一个工具页算「交付」，必须同时满足：

- 首屏工具可用，且处理全在浏览器内（零上传）。
- `live: true` 已开、sitemap 已含、GSC 已提交。
- 第 6 章验收卡全绿（含 exiftool 与 Network 面板证据）。
- Lighthouse 移动端 Performance ≥ 90、CLS < 0.1、LCP < 2.5s。
- 文案人工写过（不是模板占位、不是 AI 填充）。
- 项目 issue 里有一条交付评论，写明 URL、验收结论、已知限制。

### 1.4 ADR-lite 模板

```md
### ADR-<n>：<决策一句话>
- 背景：<2 句，为什么现在要定>
- 选择：<做了什么；被否掉的替代方案一句>
- 代价：<已知代价/欠账，以及何时回看>
```

例子：

> **ADR-1：共享编辑器用 canvas 单引擎，不做 React 状态镜像**
> 背景：照片打码要支持触摸拖框、导出与预览一致。
> 选择：`EditorEngine` 持全部状态与渲染，React 只做指针换算与工具条；否掉「React state 存 boxes」。
> 代价：React DevTools 看不到盒子状态，调试靠 `engine.currentBoxes`。

## 2. 机会调研 SOP

目标：用半天以内回答一个问题——「这个词族有没有空位，能不能在 10 个工作日内做出可用工具」。产出必须能直接填进第 3 章的一页纸。

### 2.1 关键词族扫描

1. **定种子词**：一个动词 + 一个对象（`blur face`、`redact pdf`、`remove exif`），不要用「privacy tool」这种品类词。
2. **扩修饰词**：`free` / `online` / `no watermark` / `without upload` / `ai` / `in browser`，逐个与种子词组合看 SERP。
3. **收长尾**：从 GSC（已有站）或 SERP 的 People Also Ask / 相关搜索里抄问题句，作为 FAQ 长尾，不单开文章页。
4. **产出词族表**：主词 1 个 + 副词 4-8 个 + FAQ 长尾 3-5 条，标注每个词的意图（工具型/信息型）与是否有本地处理差异点。

数据口径提醒：外部精确搜索量没有可靠公开源，不要编数字。用「SERP 里有没有专门页」和「上线 2-3 周 GSC 是否出现曝光」代替搜索量。

### 2.2 SERP 弱信号（空位判据）

在 Google 无痕窗口逐条记录，命中越多空位越大：

- [ ] 首页出现 GitHub 仓库、ProductHunt、Reddit 帖、目录页（说明没有像样的商业工具页）。
- [ ] 首页工具是「大厂功能菜单里的一个入口」（Canva/iLovePDF 的深埋页），不是独立页。
- [ ] 工具页要登录、要上传、有水印、有页数限制——且这些限制没被任何竞对当作卖点打。
- [ ] 移动端首屏是广告或长文，工具要滚两屏才出现。
- [ ] 结果语言与词族不匹配（德语站吃英文词、反之亦然）。

### 2.3 变现证据

- 竞对定价页截图：免费层限制（页数/时长/水印/批量）与付费价格。
- 公开收入/收购案例：独立开发者复盘、Acquire 列表、Similarweb 估值口径（只作量级参考）。
- 广告密度：目标 SERP 前 3 名是否挂 AdSense、广告位是否破坏体验（决定我们后挂广告的可行性）。

### 2.4 机会打分卡

每项 0-2 分，总分 ≥8 才值得写一页纸：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 词族规模 | 只有 1 个词有搜索 | 主词 + 少量副词 | 主词 + 5 个以上副词 + 长尾问题 |
| SERP 空位 | 全是成熟专站 | 混合 | 目录页/仓库/深埋功能占头部 |
| 技术可行性 | 需要服务端/重模型 | 需要 WASM 但已验证 | 纯前端 canvas/Web API 即可 |
| 变现路径 | 无付费先例 | 有付费墙但弱 | 竞对已验证付费点且价格透明 |
| 协同性 | 全新栈/新受众 | 可复用部分共享代码 | 复用现有引擎 + 同受众 + 同域权重 |

### 2.5 一页纸结论

三句话：**做什么**（一个工具，一句话）、**凭什么**（空位 + 证据）、**多久**（P0+P1 工作量）。写不出这三句就是还没调研完。

### go/no-go 硬门槛

- 必须有 ≥1 个可验证的空位信号，不能是「我觉得这个有人用」。
- 必须能纯前端实现；需要服务端存储用户文件的方案直接否（隐私承诺与成本都不成立）。
- P1 工作量 > 7 天要拆里程碑，先交最小可用版本。
- 与现有站词族重叠 > 50% 时，优先在原站加页，不新开域名。

## 4. 技术栈与脚手架标准

### 4.1 栈

- **TanStack Router + TanStack Query + React + Vite + TypeScript**。渲染形态按内容是否需要 SEO 决定：默认 SPA（客户端路由、无预渲染）；需要收录的公开页在构建期预渲染（`vite build` → SSR bundle → 静态 HTML）。同站允许混合，预渲染清单是显式路由列表，不是「所有路由」。
- 部署：Cloudflare Workers Static Assets（`wrangler.jsonc` + `_headers`；preview 自主，生产需 gate 3）。
- 样式：手写 CSS（模板用原生 CSS），不引 UI 框架（工具站首屏要轻）。
- 状态：核心逻辑在框架无关模块里，React 只做薄壳；服务端/异步数据走 TanStack Query。
- 依赖纪律：新增依赖先问「能不能 30 行手写」；能不装就不装。

### 4.2 monorepo 结构

```
microtools/
├── apps/                  # 每个站点一个目录，独立部署
├── packages/
│   ├── editor-core/       # 浏览器端打码/像素化引擎（3 个真实使用方）
│   ├── seo-kit/           # meta / JSON-LD / sitemap / robots
│   └── site-template/     # TanStack Router + Vite 双模式脚手架（SPA 默认 / 预渲染可选）
├── docs/playbook.md       # 本文件
└── docs/adr/              # 跨项目的架构决策
```

共享层准入规则（对应原则 2）：

- 进 `packages/` 的条件：已有 ≥2 个真实使用方，或成员已批准的明确计划。
- 共享包不写业务分支：站点差异用配置/组合表达。
- 改共享包接口前，在 issue 列出全部使用方与影响；破坏性变更要版本化。
- 站点代码不进共享包；共享包不 import 站点代码。

现有站点迁移边界：blurface 仍在自己的仓库部署，`packages/editor-core` 是它的代码抽包结果，接口保持一致；下次重建该站时整体迁入 `apps/`，并在迁移 issue 里核对两处实现无漂移。

### 4.3 性能门槛（每页都算）

| 指标 | 门槛 | 为什么 |
|---|---|---|
| Lighthouse 移动端 Performance | ≥ 90 | 移动端通常占 60%+ 流量 |
| CLS | < 0.1 | 工具页布局跳动会直接掉排名 |
| LCP | < 2.5s | 工具本体不能等模型/大图 |
| 首屏可交互 | 载入即可用 | 解释性文案必须在工具之后 |

模型、WASM、ffmpeg 一律 lazy load，且不参与首屏 LCP。

### 4.4 防返工约定（踩过的坑）

- **坐标系单一真源**：编辑器内部只存自然坐标（载图后 canvas 像素），UI 层用 `getBoundingClientRect` 比例换算指针坐标，不做双轨。
- **Safari 模糊**：`ctx.filter` 有兼容缺口，必须特性检测 + 降采样回退，不要 UA 嗅探。
- **模型自托管**：人脸检测模型与 WASM 放 `public/models`，运行时不请求第三方（守住「本地处理」承诺）。
- **大图保护**：长边 > 4096px 先降采样进编辑器，防移动端内存溢出。
- **图片直出**：静态资源直接用 Vite 产物，不引入运行时图片优化器（BING-16/17 的教训）。
- **字体**：用系统字体栈，不用构建期外网字体（外网依赖 + 隐私噪音）。
- **软 404 红线**：预渲染站必须用 `not_found_handling: "404-page"`；`single-page-application` 只属于 SPA 模式。模板的 `verify-render-mode.mjs` 会在构建时拦截配错。

### 4.5 新站开工（约 15 分钟到可构建）

```bash
pnpm install
pnpm new-site <app-name> --mode spa|prerender --domain https://<domain> --name "<Brand>"
pnpm --filter <app-name> dev
pnpm --filter <app-name> build   # SPA：build + 模式校验；prerender：+ 预渲染 + sitemap 校验
```

生成后立刻要改的四处：`src/lib/site.ts`（域名/品牌）、`src/lib/tool.ts`（title/H1/三步/live）、`src/lib/faq.ts`（3-5 条真实问题）、`src/components/ToolSlot.tsx`（换成真实工具）。

## 5. SEO 页面标准

> 本节只约束**预渲染模式**的公开页。登录后用户端、后台、纯交互界面按 SPA 模式做，不要求这些 SEO 结构。

### 5.1 页面结构（从上到下）

1. **首屏 = 工具本体**（Main Content）。工具就是内容，不要首屏放 hero 大图或长文。
2. **H1**：主词 + 资格词（Free / No Upload / No Watermark），一页只一个 H1。
3. **三步 how-to**，150-250 词，写实际动作，不写「我们的使命」。
4. **FAQ 3-5 条**：真实长尾疑问（合法性、隐私、格式、限制），答案 2-4 句。
5. **交叉链接**：本站其他工具页（nav + 页脚），不跨站。

### 5.2 noindex 占位流程

- 新页一律先 `live: false`：输出 `<meta name="robots" content="noindex, follow">`，且不进 sitemap。
- 工具真正可用（验收卡功能项全绿）后翻 `live: true`：noindex 消失、自动进 sitemap。
- 用 GSC「网址检查」确认状态从「已排除 - 含 noindex」变为可索引，再「请求编入索引」。
- 绝不先放开索引再补工具：空壳页被索引是最贵的返工（要等重爬）。

### 5.3 结构化数据

- 工具页：`WebApplication`（含 `isAccessibleForFree`、`offers.price = 0`）+ `FAQPage`。
- 多段用 `@graph` 合并成一块 `<script type="application/ld+json">`。
- **可见内容必须与 schema 一致**：FAQ schema 用渲染 FAQ 的同一个数组生成。
- 上线前跑 Rich Results Test，有 error 不发布。

### 5.4 title / description / canonical

- 每页 title 唯一，主词前置，品牌后缀由 `seo-kit` 统一加（页面用 `{ absolute }` 避免重复后缀）。
- description 写「做什么 + 免费 + 不上传」，不堆词。
- canonical 指向自身绝对 URL，`SITE_URL` 只有一个真源。
- OG 图 1200×630，构建期生成，不拉外部字体。

### 5.5 内链与站群纪律

- 本站内：nav 全站一致，工具页页脚互链其余工具，锚文本用工具名（不用 "click here"）。
- 跨站：**禁止**把多个工具站互链成 network。需要品牌曝光时走正常外链建设，不搞互链。
- 新页上线后不要立刻大改 slug；需要改就走 301。

### 5.6 文案纪律

- 正文人工写。禁止 AI 填充、禁止同义改写凑字数、禁止「In today's digital world」开场。
- 每个工具页至少说清三件事：能做什么、文件去哪了（本地）、有什么限制（免费层）。
- 事实性表述（合法性、格式支持）要能对上实现，写不了就不写。

## 6. 验收标准模板

复制到项目 issue，逐条勾。任何一条不绿就不算交付。

### 6.1 功能

- [ ] 输入三入口（拖拽 / 选择 / 粘贴）在桌面与移动 Safari 可用（按工具类型取舍，至少两种）。
- [ ] 效果实时预览，导出结果与预览一致。
- [ ] 导出文件名带 `redacted-` 前缀，无水印、无登录。
- [ ] 空态 / 加载态 / 错误态齐全（坏文件、超大文件、模型加载失败）。
- [ ] 触摸设备可独立完成「载入 → 处理 → 导出」全流程。
- [ ] 检测类工具：检测失败时手动模式完全可用，并有提示文案。

### 6.2 隐私

- [ ] DevTools Network 走完整流程，除本站静态资源（含 `/models/*`）外无任何出网请求。
- [ ] 无携带图片/文件字节的请求（Filter: `media`，检查 POST）。
- [ ] 导出文件无 EXIF（见 6.5）。
- [ ] `/privacy` 页写明本地处理、不收集文件、元数据剥离。

### 6.3 性能

- [ ] Lighthouse 移动端 Performance ≥ 90、CLS < 0.1、LCP < 2.5s。
- [ ] 模型 / WASM / 大依赖 lazy load，不参与 LCP。
- [ ] Lighthouse SEO / Best Practices 无 error。

### 6.4 SEO

- [ ] title / description / canonical / H1 就位且唯一。
- [ ] FAQPage + WebApplication 通过 Rich Results Test。
- [ ] `live` 已翻 true、noindex 已消失、sitemap 已含该页。
- [ ] GSC 网址检查 + 请求编入索引完成。
- [ ] 首页与其他工具页零回归（title/canonical/sitemap 不变）。

### 6.5 验收命令卡

```bash
# EXIF：期望无 GPS/LensInfo 等字段；计数为 0
exiftool redacted-example.jpg
exiftool -gps:all redacted-example.jpg | grep -c ":"   # → 0

# 零上传：DevTools → Network → 走完「载图 → 处理 → 导出」
# 允许：页面资源、/models/*.tflite、/models/wasm/*
# 禁止：任何携带文件字节的请求（Filter: media；检查 POST）

# Lighthouse（移动端）
npx lighthouse https://<domain>/<path> \
  --form-factor=mobile --throttling-method=simulate \
```

### 6.6 检测测试图集（检测类工具必过）

| 组 | 要求 |
|---|---|
| 单目标正视 | 检出 1 框，覆盖完整目标 |
| 多目标合影 | 检出率符合常识预期，漏检可手动补 |
| 无目标 | 返回空数组，UI 提示可手动 |
| 侧脸/低头/遮挡 | 允许漏检，不得误检成大框 |
| 大图 > 4096px | 载入不崩溃，检测在降采样副本上跑 |

### 6.7 常见失败模式

| 现象 | 根因 | 处置 |
|---|---|---|
| 导出有残影/接缝 | 预览与导出走两条渲染路径 | 统一到 `renderComposition` |
| Safari 上模糊无效 | 依赖 `ctx.filter` | 特性检测 + 降采样回退 |
| 移动端 OOM 崩溃 | 未降采样大图 | 长边 > 4096px 先降采样 |
| 检测框偏移 | 把显示坐标当自然坐标 | 只存自然坐标，指针处换算 |
| 页面被索引但没工具 | 先翻 live 后补功能 | live 与工具可用性绑定 |
| 上线后图片全裂 | 依赖运行时图片优化器 | 图片静态直出 |

## 7. 变现节奏

**默认：先免费无水印，拿排名与外链。** 广告与付费层在读数达标后再上（gate 4）。

### 7.1 阶段

| 阶段 | 条件 | 动作 |
|---|---|---|
| 0 免费 | 上线即 | 全功能免费、无水印、无登录；只做 SEO 与体验 |
| 1 广告 | 90 天曝光 ≥ 1,000 且移动端体验达标 | 挂 AdSense（不占首屏、不推动工具） |
| 2 付费层 | 有稳定复访 + 竞对已验证付费点 | 去水印 / 批量 / 页数时长上限 |

### 7.2 已验证付费点（来自竞对，按实现成本排序）

1. **去水印**（成本最低，用户感知强）。
2. **批量处理**（多文件一次导出）。
3. **页数 / 时长上限**（免费层限额，超出付费）。
4. 云端存储 / 历史记录（我们不做：与「零上传」承诺冲突）。

### 7.3 纪律

- 付费墙不得挡首屏 LCP，不得让免费层变成「试用」。
- 定价前先看竞对公开价格，不拍脑袋；定价与免费层变更走 gate 4。
- 广告位不放在工具与导出按钮之间；不接弹窗/插屏。
- 开启变现前确认 `/privacy` 与 cookie 提示合规（欧盟流量要能关掉个性化广告）。

## 8. kill / scale 运营手册

### 8.1 周报指标（每站每周一行）

| 指标 | 来源 | 用途 |
|---|---|---|
| 曝光 / 点击 / CTR | GSC（90 天滚动） | 判断词族是否成立 |
| 平均排名 | GSC | 判断是否在爬 |
| 收录页数 | GSC 覆盖报告 | 发现 noindex/抓取问题 |
| 移动端占比 | GSC 设备维度 | 决定性能投入优先级 |
| 首屏可用率 | 手动抽查 | 体验回归 |

周报只写「读数 + 与上周差 + 一句判断」，不写长文。

### 8.2 门槛处置（8 周读数，90 天滚动口径）

- 曝光 **≥ 1,000**：词族成立 → 加码（加副词页 / 同引擎新 preset / 语言版）。
- 曝光 **300–1,000**：观察 → 查 title/H1 与词形是否匹配，补 FAQ 长尾，不加新页。
- 曝光 **< 300**：先查收录（是否 noindex、是否进 sitemap、是否被抓取），确认收录正常且仍 < 300 才进 kill 评审。

### 8.3 kill 评审清单

1. 收录是否正常？（GSC 覆盖报告 + 网址检查）
2. 词族是否真实存在？（SERP 是否有专门页在吃这个词）
3. 是否有转化以外的价值？（外链、品牌、为其他站导流——注意不互链）
4. 沉没成本：已投入的工作日与现金。
5. 处置选项：留站观察（3 个月）/ 合并到同域其他页（301）/ 下线（410，保留 `/privacy`）。

kill 决定必须由成员拍板（gate 5）；agent 只给建议 + 数据。

### 8.4 反模式

- 曝光低就立刻改词、改 slug、改 H1（每次改动都要等重爬，等于从头再来）。
- 用「加内容」救一个没需求的工具（薄文本只会更差）。
- 同时开 3 个新站（边际成本不降，注意力被切碎）。
- 为单个站做「平台化」重构（违反原则 1/2）。

## 9. 走量实验度量口径（v1 定稿）

四个指标衡量「工厂」而不是「单个站」。每个项目结束时在 issue 里填一次，季度汇总。

### 9.1 定义

| 指标 | 定义 | 采集方式 | v1 目标 |
|---|---|---|---|
| **人工介入次数** | 需要成员做决策或纠偏的交互次数：gate 请示（1-5）+ 成员主动纠偏（文案/方向/返工）各计 1；纯 FYI、点赞、agent 之间的转交不计 | 数 issue 里 member 的决策类评论 | ≤ 6 次 / 项目 |
| **决策延迟** | 从请示评论发布 → 成员首次决策回复的小时数；取项目中位数（不含成员主动发起的讨论） | 评论 `created_at` 差值 | 中位数 < 24h |
| **立项→P1 交付周期** | 从 gate 1 批准时间 → 第一个工具页 `live: true` 合并到 main 的工作日数（不含等待成员决策的时间，另记为「外部等待」） | issue 时间戳 + PR 合并时间 | ≤ 10 个工作日 |
| **现金成本** | 该项目直接支出的现金：域名、付费服务、API、广告；不含人力与已有订阅 | 项目 issue 的成本表 | ≤ $20 / 站 / 年（首年含域名） |

### 9.2 采集纪律

- 时间戳只认平台记录（issue / comment / PR），不靠回忆补填。
- 「外部等待」单独记录：它衡量成员侧瓶颈，不惩罚 agent 的执行周期。
- 现金成本发生前必须有 gate 2 批准记录；无批准记录的支出视为事故。
- 季度汇总看趋势，不用单项目数据下结论（样本太小）。

### 9.3 报表格式（季度）

```md
## 季度走量报表 <YYYY-Qn>
| 项目 | 介入次数 | 决策延迟中位数 | 立项→P1（工作日） | 外部等待 | 现金成本 | 90 天曝光 |
|---|---|---|---|---|---|---|
| <站名> | 5 | 6h | 8 | 2d | $12 | 1,748 |

结论：<一句话，例如「边际成本主要在 P1 引擎，不在 IA/SEO」>
下一步：<一个动作>
```

## 附录 B：反模式速查

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 为「以后可能复用」提前抽包 | 违反原则 1/2，抽象没有真实使用方 | 留在项目内，第二个使用者出现再抽 |
| React state 与引擎各存一份 boxes | 双真源漂移，导出与预览不一致 | 状态只在引擎，UI 读快照 |
| 先放开索引再补功能 | 空壳页被索引，返工要等重爬 | `live` 与工具可用性绑定 |
| 用 AI 生成 FAQ 凑条数 | 核心更新打击薄文本，且 schema 与内容易不一致 | 人工写真实长尾问题 |
| 多站互链 | 站群操纵排名，风险高于收益 | 本站内互链，外链靠内容 |
| 依赖运行时图片优化器不验证 | Workers 上 500，全站裂图 | 图片静态直出 |
| 曝光低就改 slug/词族 | 每次改动重置抓取与评估 | 先查收录，再等 8 周读数 |
